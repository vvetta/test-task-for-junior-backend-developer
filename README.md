# Task Service

Сервис для управления задачами с HTTP API на Go.

## Требования

- Go `1.23+`
- Docker и Docker Compose

## Быстрый запуск через Docker Compose

```bash
docker compose up --build
```

После запуска сервис будет доступен по адресу `http://localhost:8080`.

Если `postgres` уже запускался ранее со старой схемой, пересоздай volume:

```bash
docker compose down -v
docker compose up --build
```

Причина в том, что SQL-файл из `migrations/0001_create_tasks.up.sql` монтируется в `docker-entrypoint-initdb.d` и применяется только при инициализации пустого data volume.

Базовый префикс API:

/api/v1

# Task Service (Новая фича)

В рамках тестового задания в проект добавлена поддержка периодических задач без введения новых HTTP-ручек. Для работы с обычными и периодическими задачами используются те же endpoints `/api/v1/tasks`.

## Что реализовано

Поддержаны следующие типы периодичности:

- ежедневные задачи, каждый `n`-й день
- ежемесячные задачи на конкретное число месяца от `1` до `30`
- задачи на конкретные даты
- задачи на четные или нечетные дни месяца

## Основная идея решения

Я сохранил существующий API и расширил текущую модель задач.

В системе теперь есть три типа записей:

- `single` - обычная разовая задача
- `template` - шаблон периодической задачи
- `instance` - конкретный экземпляр задачи, созданный из шаблона

Шаблон и экземпляры хранятся в таблице `tasks`. Дополнительные настройки периодичности вынесены в отдельную таблицу `task_recurrence_rules`.

Такой подход позволяет:

- не ломать существующие маршруты
- не вводить отдельный ресурс для периодических задач
- сохранить совместимость с уже существующим CRUD
- явно разделить шаблон и реальные рабочие задачи

## Как работает периодическая задача

При создании задачи:

- если поле `recurrence` отсутствует, создается обычная задача `single`
- если поле `recurrence` присутствует, создается шаблон `template`

После создания шаблона сервис генерирует набор задач-экземпляров `instance` на ограниченный горизонт вперед.

Каждый экземпляр:

- имеет `parent_task_id`, указывающий на шаблон
- имеет дату `scheduled_for`
- создается как обычная рабочая задача

## Почему используется ограниченный горизонт генерации

Система не создает бесконечное число задач вперед.

Вместо этого используется генерация на ограниченный период вперед. Это сделано специально, чтобы:

- не раздувать базу данных
- не создавать тысячи лишних записей
- оставить возможность регулярно догенерировать будущие экземпляры

Для этого в правиле периодичности хранится поле `last_generated_for`.

## Принятые допущения

Так как в задании не все требования детализированы, были приняты следующие допущения.

### 1. Новые ручки не добавляются

Фича реализована через существующие маршруты:

- `POST /api/v1/tasks`
- `GET /api/v1/tasks`
- `GET /api/v1/tasks/{id}`
- `PUT /api/v1/tasks/{id}`
- `DELETE /api/v1/tasks/{id}`

### 2. Периодическая задача представлена шаблоном

Периодическая задача сама по себе не является рабочей задачей для врача. Рабочими являются только экземпляры, созданные из шаблона.

### 3. По умолчанию список задач возвращает рабочие задачи

`GET /api/v1/tasks` по умолчанию возвращает:

- `single`
- `instance`

Шаблоны можно получить отдельно:

- `GET /api/v1/tasks?kind=template`

Для отладки можно запросить все записи:

- `GET /api/v1/tasks?kind=all`

### 4. Удаление шаблона является деактивацией

Если удалить шаблон через `DELETE /api/v1/tasks/{id}`, он не удаляется физически из базы, а деактивируется.

Это означает:

- новые экземпляры больше не генерируются
- уже созданные экземпляры сохраняются

### 5. Изменение шаблона не переписывает уже созданные экземпляры

При обновлении шаблона меняются только будущие срабатывания.

Уже созданные экземпляры автоматически не пересоздаются и не модифицируются.

### 6. Для ежемесячных задач допустимы только числа от 1 до 30

Это соответствует формулировке тестового задания.

### 7. Четность определяется по числу месяца

Например:

- `2`, `4`, `6` - четные дни месяца
- `1`, `3`, `5` - нечетные дни месяца

### 8. Для каждого типа периодичности разрешены только свои поля

Например:

- `daily` использует `every_n_days`
- `monthly` использует `day_of_month`
- `day_parity` использует `parity`
- `specific_dates` использует `specific_dates`

Передача полей другого режима считается ошибкой валидации.

### 9. Таймзона хранится как часть правила

Поле `time_zone` используется для корректного расчета текущей даты и дальнейшей генерации задач.

## Структура хранения данных

### Таблица `tasks`

Содержит все задачи:

- обычные задачи
- шаблоны периодических задач
- экземпляры периодических задач

Дополнительные поля:

- `kind`
- `scheduled_for`
- `parent_task_id`
- `is_active`

### Таблица `task_recurrence_rules`

Содержит настройки периодичности для шаблонов:

- `recurrence_type`
- `start_date`
- `end_date`
- `time_zone`
- `every_n_days`
- `day_of_month`
- `day_parity`
- `specific_dates`
- `last_generated_for`

## Защита от дублей

Для экземпляров используется уникальность по:

- `parent_task_id`
- `scheduled_for`

Это позволяет безопасно повторно запускать генерацию без риска создать дубликаты.
